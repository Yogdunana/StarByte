# StarByte 计算机协会管理系统 — 总体架构设计

> **版本**: v1.0
> **日期**: 2026-08-24
> **状态**: 一期设计

---

## 1. 项目概述

StarByte 是一个面向高校计算机协会的全功能管理系统，涵盖入会申请、人员档案、面试管理、任务流转、会议投票、合同管理、纪律处分、IT 实习、财务管理等协会日常运营的方方面面。

系统采用模块化设计，底层 OA 流程引擎为核心，支持拖拽式流程配置，以适应不同届管理层的差异化需求。

### 3.2 架构原则

1. **模块化**：每个业务模块自包含，通过明确定义的接口交互
2. **插件化**：流程引擎、通知渠道、权限策略等均采用插件/策略模式，便于扩展
3. **配置化**：避免硬编码，所有业务配置（权限开关、流程定义、通知模板等）均可动态配置
4. **事件驱动**：核心业务动作触发领域事件，通知、审计、统计等通过订阅事件解耦
5. **可扩展性**：二期功能预留接口，数据模型预留扩展字段

### 4.2 后端模块分层规范

每个业务模块遵循统一的四层架构：

```
module/
├── handler/        # 接口层：处理 HTTP 请求，参数校验，调用 service
├── service/        # 业务逻辑层：核心业务逻辑，事务控制，调用 repo
├── repo/           # 数据访问层：数据库 CRUD，GORM 操作
├── model/          # 数据模型层：数据库表结构定义（GORM Model）
└── dto/            # 数据传输对象：请求/响应结构体定义
```

**依赖方向**：handler → service → repo → model
**禁止反向依赖**，不允许 repo 层调用 service 层。

## 5. 核心模块设计概要

### 5.1 用户系统

- **主键策略**：UUID v4，不使用自增 ID
- **多身份关联**：一个用户可关联多个学号（本科/研究生），通过 `user_identities` 表管理
- **登录方式**：账号密码（一期），预留第三方登录接口（微信扫码等）
- **密码加密**：bcrypt
- **Token 机制**：Access Token（15分钟） + Refresh Token（7天），支持黑名单

### 5.2 RBAC 权限系统

- **模型**：用户 → 角色 → 权限，支持多角色
- **权限粒度**：API 级 + 数据级（部门数据权限）
- **配置化**：所有权限和角色均可在后台管理页面配置，不硬编码
- **权限开关**：每个功能模块都有独立的权限开关，由社长/管理员控制

### 5.3 流程引擎（核心）

- **节点插件化**：每个节点类型实现统一的 `NodeHandler` 接口，新增节点类型无需改核心代码
- **节点类型**：
  - 开始节点、结束节点
  - 审批节点（单人审批 / 多人会签 / 多人或签 / 比例通过）
  - 条件分支节点（表达式判断）
  - 并行网关（多条路径同时执行）
  - 任务节点（自动执行预设动作，如发通知、更新数据）
- **表达式引擎**：基于 govaluate，支持条件判断
- **事件驱动**：流程启动、任务创建、审批通过、流程结束等均触发领域事件
- **版本管理**：流程定义支持多版本，已运行的实例使用启动时的版本

### 5.4 通知系统

- **策略模式**：多种通知渠道实现统一的 `Notifier` 接口
- **渠道类型**：
  - 站内消息（数据库存储，必选）
  - WebSocket 实时推送（必选）
  - 邮件通知（SMTP，一期）
  - 预留：微信公众号、企业微信、短信（二期）
- **通知模板**：支持模板配置，变量替换
- **已读状态**：站内消息支持已读/未读

### 5.5 审计日志

- **记录范围**：
  - 所有写操作（POST / PUT / DELETE）
  - 登录 / 登出
- **记录内容**：操作人ID、操作时间、IP地址、User-Agent、请求路径、请求方法、请求参数、响应状态码、响应结果（可选）、耗时
- **实现方式**：Gin 中间件自动拦截，异步写入数据库
- **查询**：支持按操作人、操作类型、时间范围、IP 等维度检索

## 7. API 设计规范

### 7.1 统一响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "uuid-string",
  "timestamp": 1234567890
}
```

- `code`: 0 表示成功，非 0 表示错误
- `message`: 错误描述，成功时为 "success"
- `data`: 响应数据，失败时可为 null
- `request_id`: 请求唯一标识，用于排查问题
- `timestamp`: 响应时间戳

### 7.2 错误码规范

| 错误码范围 | 说明 |
|-----------|------|
| 0 | 成功 |
| 1000-1999 | 通用错误（参数错误、未授权、禁止访问、不存在等） |
| 2000-2999 | 用户模块错误 |
| 3000-3999 | 权限模块错误 |
| 4000-4999 | 流程引擎错误 |
| 5000-5999 | 业务模块错误（按子模块再细分） |

### 7.3 RESTful API 命名规范

- 使用复数名词：`/api/v1/users` 而非 `/api/v1/user`
- 使用 HTTP 动词表达操作：GET（查询）、POST（创建）、PUT（更新）、DELETE（删除）
- 层级关系用路径：`/api/v1/departments/{deptId}/members`
- 过滤/排序/分页用 Query 参数

## 9. 非功能性需求

### 9.1 安全
- 密码 bcrypt 加密存储
- JWT 签名验证 + Refresh Token 机制
- SQL 注入防护（GORM 参数化查询）
- XSS 防护（前端转义 + 后端校验）
- CSRF 防护（JWT 机制天然免疫）
- 接口限流（Redis + 令牌桶）

### 9.2 性能
- 热点数据 Redis 缓存
- 数据库索引优化
- 分页查询
- 异步处理（审计日志、通知发送等）

### 9.3 可扩展性
- 模块化架构，新增模块不影响现有模块
- 插件化设计，流程节点、通知渠道可扩展
- 配置化，业务规则不硬编码
