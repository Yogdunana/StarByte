# PR 规范说明

> **版本**: v1.0
> **日期**: 2026-08-24
> **适用范围**: StarByte 全项目

---

## 1. PR 提交前检查清单

提交 PR 之前，请确认以下事项：

- [ ] 代码遵循项目开发规范（后端规范 / 前端规范）
- [ ] 本地运行通过，功能已自测
- [ ] 没有 console.log / println 等调试代码
- [ ] 没有硬编码的密码、密钥等敏感信息
- [ ] 必要的文档已更新
- [ ] 命名符合规范（变量、函数、文件、组件等）
- [ ] 没有注释掉的大段代码
- [ ] PR 大小合理（建议不超过 500 行）
- [ ] 已同步 main 分支最新代码，没有冲突

## 2. PR 标题规范

格式：`type(scope): subject`

| type | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug 修复 |
| docs | 文档更新 |
| style | 代码格式调整 |
| refactor | 代码重构 |
| perf | 性能优化 |
| test | 测试相关 |
| chore | 构建/工具/依赖 |

示例：
- `feat(workflow): 增加条件分支节点支持`
- `fix(user): 修复用户列表分页参数错误`
- `docs: 更新后端开发规范`
- `chore(deps): 升级 Gin 到 v1.10.0`

## 4. Code Review 指南

### 4.1 Reviewer 职责
- 认真阅读代码，不要随便 Approve
- 关注代码质量、逻辑正确性、安全性、可维护性
- 有疑问及时提出，不要憋着
- 好的代码也要表扬，鼓励团队士气

### 4.2 常见检查点

**代码质量**
- [ ] 命名是否清晰、符合规范
- [ ] 函数是否太长，是否可以拆分
- [ ] 有没有重复代码
- [ ] 注释是否适当（不要过多，也不要没有）
- [ ] 错误处理是否完善
- [ ] 边界条件是否考虑到

**业务逻辑**
- [ ] 需求理解是否正确
- [ ] 逻辑是否有漏洞
- [ ] 异常场景是否处理
- [ ] 数据一致性是否保证

**安全性**
- [ ] 权限校验是否到位
- [ ] 输入是否校验（防止注入）
- [ ] 敏感信息是否泄露
- [ ] 有没有 SQL 注入、XSS 等风险

**性能**
- [ ] 有没有 N+1 查询
- [ ] 大数据量是否分页
- [ ] 有没有不必要的循环或计算

**可维护性**
- [ ] 模块划分是否合理
- [ ] 接口设计是否清晰
- [ ] 有没有硬编码（配置化）
- [ ] 扩展性好不好

### 4.3 Review 评论规范
- 明确指出问题位置和原因
- 给出具体的改进建议
- 语气友好，尊重他人
- 使用 suggestion 功能直接给出修改建议
- 不是问题但可以优化的点，标为「建议」

### 4.4 PR 作者职责
- 及时回复 Review 评论
- 有不同意见可以讨论，不要直接忽略
- 修改后回复「已修改」并 @Reviewer
- 不要直接 force push 已经被 review 的提交（除非协商好）

## 5. 合并规范

### 5.1 合并方式
- 使用 **Squash Merge**（压缩合并）
- 一个 PR 对应 main 分支上的一个 commit
- 合并后自动删除源分支

### 5.2 合并条件
- ✅ 至少 1 个 Approve（核心模块需要 2 个）
- ✅ CI 检查全部通过
- ✅ 所有评论都已解决
- ✅ 没有合并冲突
- ✅ PR 作者自己确认没问题

### 5.3 谁来合并
- 一般由 PR 作者自己合并（满足条件后）
- 或者由 Reviewer 合并
- 核心模块的 PR 需要 Maintainer 合并

## 6. 常见问题

### Q: PR 太大了怎么办？
A: 尽量拆成多个小 PR。可以先做基础功能，再做高级功能，逐步合入。如果是同一个大功能，可以先合到一个 feature 分支，最后再统一合 main。

### Q: Review 意见不同意怎么办？
A: 先在 PR 评论里讨论，讲道理。如果讨论不出结果，找技术负责人拍板。不要赌气不修改，也不要随便妥协。

### Q: 紧急 bug 能不能跳过 Review？
A: 尽量不要。如果真的很急，至少找一个人快速看一眼。hotfix 分支合入 main 后也要补 Review。

### Q: 已经合并了但发现 bug 怎么办？
A: 新开一个 fix/ 分支修复，提新的 PR。不要直接改 main。
